# Copy OpenVLA's Stock Scripts, Write 200 Lines

Roughly 90% of the "Forgetting to Refuse" (FTR) pipeline already exists as small, self-contained files in `openvla/openvla` at commit `c8f03f4`, and the fastest 10-day path is to copy those files nearly verbatim and add about 200 lines of new code rather than adopt any framework or fork. Reuse unchanged: the action tokenizer, the padded collator, the prompt builder, the three HF `*_prismatic.py` model files, the load-and-LoRA-wrap and training-loop blocks of `vla-scripts/finetune.py`, and the entire LIBERO eval quartet (`run_libero_eval.py`, `libero_utils.py`, `robot_utils.py`, `openvla_utils.py`). Write thin adapters for four things: a **~40-line map-style Dataset cloned from `DummyDataset`** that pre-normalizes actions with the frozen `libero_spatial` q01/q99 and exposes them under that key; a **~15-line `predict_action` variant** that returns the seven generated token ids alongside the unnormalized action (they are a local variable at `modeling_prismatic.py` L521); a **~40-line violation wrapper** over LIBERO-Safety's `info['cost']` after the one-line Issue #3 patch, re-evaluating each constraint yourself because the dict collapses same-named predicates; and a **~2-line reseed** before every `env.reset()`. Write from scratch only the no-op label generator (`tokenize(normalize(0, libero_spatial))`), the scripted-contact fixture (~30 lines on robosuite's `transform_utils`), the BDDL twins, a ~15-line cluster bootstrap on `scipy.stats.bootstrap(paired=True)`, and stdlib provenance (`hashlib` + `os.replace` + `pyarrow` schema metadata). Among data routes, a **plain `torch.utils.data.Dataset` beats RLDS and the LeRobot converter** for both the alignment and personalization arms, because the plan's frozen-stats requirement forces a code patch on the RLDS path anyway and the converter adds TF friction plus a key-naming reconciliation nobody has run end to end. The environment is the real risk, not the code: pin the mid-2024 stack (Python 3.10, torch 2.2.0 cu121, transformers 4.40.1, peft 0.11.1, flash-attn 2.5.5 built from source, mujoco 2.3.7, numpy 1.26.4, robosuite 1.4.1) on `nvidia/cuda:12.1.1-cudnn8-devel-ubuntu22.04` with `MUJOCO_GL=egl`, on a **RunPod secure A100 80 GB at $1.59/h**, and expect T2-shape compute of roughly $70 to $90. Two findings change PLAN.md: the LIBERO-Safety HF dataset is **not usable as the benign-movement source** (TSA and FSHOA are pooled under identical task strings and its actions are raw meter deltas for a different controller), so go straight to the pre-declared fallback; and you should **never install LIBERO-Safety's vendored robosuite**, whose only difference from upstream 1.4.0 is an `osc_pose.json` with `output_max ±2` and `kp 750` that would turn OpenVLA's ±0.94 commands into two-metre steps.

## Nine stock files cover training, eval and merge; four thin adapters close the gaps

The training side is a single 370-line draccus script whose every CLI flag is a `FinetuneConfig` field, and its useful parts are cleanly separable. Lines 150-192 register the Auto classes, load the base in bf16, and wrap it with `LoraConfig(r=32, lora_alpha=min(r,16), lora_dropout=0.0, target_modules="all-linear", init_lora_weights="gaussian")`; lines 249-318 are the autocast training step with native gradient accumulation and a constant-LR `AdamW`; lines 320-364 save the processor and adapter, reload a fresh bf16 base, `PeftModel.from_pretrained(...).merge_and_unload()`, and `save_pretrained` ([finetune.py](https://github.com/openvla/openvla/blob/c8f03f4/vla-scripts/finetune.py)). Loss masking lives in the batch transform, not the model: `labels[: -(len(action) + 1)] = IGNORE_INDEX` supervises exactly the seven action tokens plus `</s>` ([datasets.py L31-67](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/datasets.py#L31-L67)), and the maintainers confirm only those seven logits enter the cross-entropy ([openvla#147](https://github.com/openvla/openvla/issues/147)). The collator `PaddedCollatorForActionPrediction` right-pads `input_ids` with the pad id and `labels` with -100 and builds the attention mask ([data_utils.py L95-142](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/util/data_utils.py#L95-L142)); `ActionTokenizer` clips to [-1, 1], `np.digitize`s into 256 bins, and maps bin `b` to token `vocab_size - b`, with `action_token_begin_idx = 31743` ([action_tokenizer.py L13-68](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/action_tokenizer.py#L13-L68)); `PurePromptBuilder` wraps the human turn as `In: {msg}\nOut: ` and the model turn as `{msg}</s>` ([base_prompter.py L28-37](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/models/backbones/llm/prompting/base_prompter.py#L28-L37)). None of these needs an edit.

The one gap on the training side is the dataset, and the maintainers ship its contract. `DummyDataset` (datasets.py L180-232) is a map-style Dataset whose `__getitem__` builds the prompt with `add_turn("human", f"What action should the robot take to {instruction}?")` and `add_turn("gpt", self.action_tokenizer(action))`, tokenizes with `add_special_tokens=True`, masks labels from the end, applies `image_transform` to a PIL image, and returns `dict(pixel_values, input_ids, labels)`; it also carries `self.dataset_statistics` so `save_dataset_statistics` can write the JSON that inference needs ([datasets.py L180-232](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/datasets.py#L180-L232); [finetune.py L195-207](https://github.com/openvla/openvla/blob/c8f03f4/vla-scripts/finetune.py#L195-L207)). Your copy must do four things the stub does not: normalize dims 0-5 with the frozen `libero_spatial` q01/q99 (`clip(2*(a-q01)/(q99-q01)-1, -1, 1)`) and leave the gripper in [0, 1] with +1 = open, mirroring `libero_dataset_transform` and the `[True]*6 + [False]` mask ([transforms.py L827-841](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/rlds/oxe/transforms.py#L827-L841); [materialize.py L39](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/rlds/oxe/materialize.py#L39)); set `self.dataset_statistics = {"libero_spatial": <the checkpoint's action block>}` copied from the released `config.json` ([HF config.json](https://huggingface.co/openvla/openvla-7b-finetuned-libero-spatial/blob/main/config.json)); feed 224×224 images rotated 180° that have been through the same `get_libero_image` + center-crop path the evaluator uses, so train and test preprocessing are the same two reused functions ([libero_utils.py L33-58](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/libero/libero_utils.py#L33-L58); [openvla_utils.py L81-170](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/openvla_utils.py#L81-L170)); and wrap the loop in epochs with `num_workers > 0`, because `finetune.py` iterates the dataloader once and the RLDS loader repeats implicitly ([finetune.py L207-210](https://github.com/openvla/openvla/blob/c8f03f4/vla-scripts/finetune.py#L207-L210)). Category proportions (harmful no-op, benign stop, movement, rehearsal) are then plain `ConcatDataset` + `WeightedRandomSampler`, with no OpenVLA weight math. Add one line the stock script lacks: `clip_grad_norm_(trainable_params, 1.0)` before `optimizer.step()`, which an open issue identifies as the fix for LoRA runs that hit 100% token accuracy and 0% LIBERO success after a loss spike at LR 5e-4 ([openvla#333](https://github.com/openvla/openvla/issues/333); [PR #334](https://github.com/openvla/openvla/pull/334); [openvla#299](https://github.com/openvla/openvla/issues/299)).

Nothing external supplies refusal labels. Every VLA-safety repo found is a different simulator or has no code (SafeVLA on AI2-THOR, HazardArena on dm_control, SafeManip on RoboCasa with no license, SafeVLA-Bench/RedVLA/VLA-Forget/ForesightSafety with no release), so the no-op generator is from-scratch and trivial: the six pose targets are `np.digitize(2*(0-q01)/(q99-q01)-1, bins)` under `libero_spatial`, which lands near bins 113/110/128/130/138/143 rather than six copies of 128, and the gripper target is "unchanged" ([SafeVLA README](https://github.com/PKU-Alignment/SafeVLA); [HazardArena](https://github.com/HazardArena-Team/HazardArena); [SafeManip](https://github.com/chengyuehuang511/SafeManip); [action_tokenizer.py](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/action_tokenizer.py)). The only one-line idea worth taking from RoboShackles is to build the zero before normalization, which the encoded-zero recipe already does.

The eval quartet is reusable almost unchanged and is small (~290 + 100 + 100 + 170 lines). It builds one `OffScreenRenderEnv` per task at 256 px, calls `env.seed(0)`, runs `env.reset()` then `env.set_init_state(initial_states[episode_idx])`, steps ten dummy actions `[0,0,0,0,0,0,-1]` "because the simulator drops objects", rotates the image 180°, JPEG-roundtrips and lanczos3-resizes to 224, center-crops 0.9 if `--center_crop True`, calls `vla.predict_action(**inputs, unnorm_key=..., do_sample=False)`, maps the gripper [0,1]→{-1,+1} and sign-flips it, and stops on `done` ([run_libero_eval.py L136-238](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/libero/run_libero_eval.py#L136-L238); [libero_utils.py L18-58](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/libero/libero_utils.py#L18-L58); [robot_utils.py L75-102](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/robot_utils.py#L75-L102)). The `unnorm_key` logic already handles both `libero_spatial` and `libero_spatial_no_noops` ([run_libero_eval.py L100-112](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/libero/run_libero_eval.py#L100-L112)), and `get_vla` loads `<ckpt>/dataset_statistics.json` into `vla.norm_stats` if present ([openvla_utils.py L31-72](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/openvla_utils.py#L31-L72)). The port to LIBERO-Safety is mechanical: its `Benchmark` exposes `get_task_init_states(level, i)` and `get_task_bddl_file_path(level, i)` and loads with `torch.load(..., weights_only=False)`; `get_benchmark("obstacle_avoidance_human")()` returns the flattened L0+L1+L2 list, and the five FSHOA L0 task names are in `vla_safety_task_map.py` ([LIBERO-Safety benchmark/__init__.py](https://github.com/LIBERO-SAFETY/LIBERO-Safety/blob/main/libero/libero/benchmark/__init__.py); [vla_safety_task_map.py](https://github.com/LIBERO-SAFETY/LIBERO-Safety/blob/main/libero/libero/benchmark/vla_safety_task_map.py)). The FSHOA L0 moka-pot `.pruned_init` is a torch tensor of shape **(50, 60)**, so the plan's "~50 states per task" assumption holds ([libero_apis note, decoded from the pickle](https://github.com/LIBERO-SAFETY/LIBERO-Safety/tree/main/libero/libero/init_files)). The instruction-sensitivity probe for Gate A needs no perturbation library: LIBERO-plus's language variants are BDDL copies differing only on the `:language` line, mapped back to the base `.pruned_init` by stripping a `_language_N` suffix, and LIBERO-PRO's `LanguagePerturbator` is a regex on `\(:language\s*(.*?)\)`; both mechanisms are two lines inside the stock loop, and a blank instruction parses fine because `bddl` lower-cases and whitespace-splits the file ([LIBERO-plus benchmark/__init__.py L189-231](https://github.com/sylvestf/LIBERO-plus/blob/main/libero/libero/benchmark/__init__.py); [LIBERO-PRO perturbation.py](https://github.com/Zxy-MLlab/LIBERO-PRO/blob/master/perturbation.py); [bddl parsing.py](https://github.com/StanfordVL/bddl/blob/master/bddl/parsing.py)).

The violation signal needs the most care. LIBERO-Safety's `step()` computes `cost = self._check_constraint(done)` and writes `info['cost']`, a dict keyed by lower-cased predicate name and evaluated only while `not done` ([bddl_base_domain.py L925-932, L1251-1259](https://github.com/LIBERO-SAFETY/LIBERO-Safety/blob/main/libero/libero/envs/bddl_base_domain.py)). Three consequences drive the wrapper design. First, `check_robot_contact` collects integer geom ids into `g_group` while `_check_contact` compares names, so `cost['checkrobotcontact']` is always 0 on `main`; the fix is `g_group.append(g_name)` at the two append lines (L1062, L1064), and the reporter scripted the arm into an object for ~40 steps and saw 110-113 contact pairs with the predicate still False ([Issue #3](https://github.com/LIBERO-SAFETY/LIBERO-Safety/issues/3)). Second, every FSHOA L0 task has three `CheckContact` constraints plus one `CheckRobotContact`, and because the dict is keyed by predicate name, the three `CheckContact` entries collapse to a single value equal to the last one evaluated; your wrapper should loop `for c in env.env.parsed_problem['constraints']: env.env._eval_predicate(c)` and record each pair separately ([FSHOA L0 BDDL](https://github.com/LIBERO-SAFETY/LIBERO-Safety/blob/main/libero/libero/bddl_files/obstacle_avoidance_human/L0/put_both_moka_pots_on_the_stove.bddl)). Third, cost is suppressed on the success step and the env never terminates on cost, so "violation ends the episode" is your loop's job. The fallback detector, if the fork fails to install, is a ~20-line scan modelled on robosuite's `check_contact`/`get_contacts` but on geom **ids** built once from `sim.model.geom_name2id`, which sidesteps the exact id/name confusion behind Issue #3 ([robosuite sim_utils.py](https://github.com/ARISE-Initiative/robosuite/blob/master/robosuite/utils/sim_utils.py)). The fixture helper is a proportional loop on `robosuite.utils.transform_utils.get_pose_error` emitting `clip(K*err, -1, 1)` as the six OSC dims, then N "press" steps along the hand normal; the hold fixture is the all-zero action over the horizon ([transform_utils.py](https://github.com/ARISE-Initiative/robosuite/blob/master/robosuite/utils/transform_utils.py)). BDDL twins that only edit `:language` share the original `.pruned_init`; twins that add or remove an object change `1 + nq + nv` and invalidate it, so the comparator cue must either keep the object set fixed or regenerate init states with LIBERO-PRO's 30-line recipe (`OffScreenRenderEnv` N times, `get_sim_state()`, pickle into a zip as `archive/data.pkl`), accepting that the pair is then no longer state-identical ([LIBERO-PRO generate_init_states.py](https://github.com/Zxy-MLlab/LIBERO-PRO/blob/master/notebooks/generate_init_states.py)).

Token capture is a 15-line helper, not a model change. `predict_action` appends token 29871 if absent, calls `self.generate(input_ids, max_new_tokens=7, **kwargs)`, slices `generated_ids[0, -7:]`, computes `vocab_size - id`, `clip(bin - 1, 0, 254)`, indexes `bin_centers`, and unnormalizes where `mask` is True, returning only the array; the ids are a local at L521 ([modeling_prismatic.py L506-536](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/extern/hf/modeling_prismatic.py#L506-L536)). Calling `vla.generate` yourself with the same arguments and applying the same four lines gives tokens and action from one pass at zero extra compute; if you want per-token logits for entropy, `return_dict_in_generate=True, output_scores=True` works when you call `generate` directly and read `.sequences`/`.scores`, but not when passed through `predict_action`'s `**kwargs`, and its behaviour under transformers 4.40.1 with flash-attn is unverified. Action tokens occupy ids 31744-31999 in the 32000-token LLaMA vocabulary ([openvla-oft constants.py L11-13](https://github.com/moojink/openvla-oft/blob/e4287e9/prismatic/vla/constants.py#L11-L13)).

The merge lifecycle is already in the stock script, but its defaults are wrong for a sprint. Merging runs at every `save_steps` on every rank, each time loading a full 7B bf16 base on CPU; the final weights are never saved if `max_steps` is not a multiple of `save_steps`; and the merged `config.json` still carries the base model's 25 OXE `norm_stats` keys because `save_pretrained` is called on a base loaded from `cfg.vla_path`, which is exactly the assertion users hit in issues #87 and #274 ([finetune.py L320-369](https://github.com/openvla/openvla/blob/c8f03f4/vla-scripts/finetune.py#L320-L369); [openvla#87](https://github.com/openvla/openvla/issues/87); [openvla#274](https://github.com/openvla/openvla/issues/274)). Set `save_steps == max_steps`, set `merged_vla.config.norm_stats = {"libero_spatial": stats}` before `save_pretrained`, and keep `dataset_statistics.json` alongside. `save_pretrained` does not copy the remote-code files, so either register the Auto classes as `finetune.py` L152-155 does before loading the merged dir, or copy `configuration/modeling/processing_prismatic.py` into it ([openvla#312](https://github.com/openvla/openvla/issues/312)). The second stage is then `finetune.py --vla_path <merged_dir>`, which re-wraps with a fresh `LoraConfig` at L172-182. For the Gate B "merge → fresh adapter → reload: no drift" check, the cheapest comparator is inference with the adapter attached and unmerged (`PeftModel.from_pretrained(base, adapter_dir)`), since bf16 merge fidelity has PEFT-level fixes but no OpenVLA-specific measurement ([peft PR #2433](https://github.com/huggingface/peft/pull/2433)). openvla-oft's `merge_lora_weights_and_save.py` is a clean 73-line standalone if you prefer an offline merge ([OFT merge script](https://github.com/moojink/openvla-oft/blob/e4287e9/vla-scripts/merge_lora_weights_and_save.py)).

For analysis and provenance, stdlib plus SciPy and pyarrow is the whole dependency set. `scipy.stats.bootstrap` with `paired=True` resamples one index array across all inputs and bounds memory with `batch`; it has no cluster mode, so aggregate each arm to one value per init state (the plan's 50 states × 4 templates gives equal clusters) and pass `statistic=lambda a, b, axis: (a - b).mean(axis)`; the docs warn that BCa returns NaN when the bootstrap distribution is degenerate, which all-zero arms will trigger, so fall back to `method='percentile'` and log the fallback ([SciPy bootstrap docs](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)). Seaborn's `lineplot(units=seed, estimator=None)` is the per-seed idiom ([seaborn docs](https://seaborn.pydata.org/generated/seaborn.lineplot.html)). Pingouin is GPL-3.0 and bootstrapx is seven months old with six stars; neither is worth adopting ([pingouin](https://github.com/raphaelvallat/pingouin); [bootstrapx](https://github.com/artyerokhin/bootstrapx)). Provenance is `yaml.safe_load` into a frozen dataclass, the resolved config dumped as canonical JSON and sha256-hashed, tables written with `pq.write_table` after `table.schema.with_metadata({config_hash, git_sha})` to a temp path then `os.replace`d into place, so `pq.read_metadata` alone identifies any table ([PyArrow Parquet docs](https://arrow.apache.org/docs/python/parquet.html); [os.replace](https://docs.python.org/3/library/os.html#os.replace)). `atomicwrites` has been archived since 2022 ([python-atomicwrites](https://github.com/untitaker/python-atomicwrites)). Because both copied scripts already call `wandb.init`, `WANDB_MODE=offline` gives loss curves with zero new code, and the run table comes from your Parquet, not the tracker ([W&B offline](https://docs.wandb.ai/support/models/articles/how-do-i-run-wandb-offline)). Keep `draccus` only inside the copied scripts (it is pinned at 0.8.0 by the openvla install) and use `argparse` for new entry points; adding tyro, typer, pydantic-settings, Hydra, MLflow or DVC buys nothing for a single-researcher, single-box sprint. Video stays on `imageio.get_writer(mp4_path, fps=30)` so rollouts are byte-for-byte OpenVLA's pipeline ([libero_utils.py L61-74](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/libero/libero_utils.py#L61-L74)).

## A plain torch Dataset beats RLDS and the LeRobot converter for both training arms

The README recommends RLDS "for most users" because that loader "is tested more extensively," and offers the custom-Dataset path as option (b) ([README L205-208](https://github.com/openvla/openvla/blob/c8f03f4/README.md)). For this project the ranking inverts, for one structural reason: PLAN.md fixes the normalization key to `libero_spatial` for every arm, and `finetune.py` **always recomputes** statistics from the RLDS data with no CLI override; `make_dataset_from_rlds` accepts a `dataset_statistics` path, but nothing in `RLDSDataset` or `finetune.py` passes one ([rlds/dataset.py L51, L205-222](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/rlds/dataset.py); [datasets.py L101-119](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/datasets.py)). A post-hoc overwrite of `dataset_statistics.json` would not fix it, because the tokens the model was trained on would have been produced under the recomputed stats. So even the "tested" route needs a code patch for the personalization arm on `libero_object_no_noops`, and the alignment arm would additionally need a TFDS builder (`tfds build`, `tensorflow==2.15.0`, `tensorflow_datasets==4.9.3`) plus edits to `configs.py` and `transforms.py` before the loader recognizes the name, with mixture weights that are multiplied by dataset size because `balance_weights=True` is hard-coded ([materialize.py L31, L70](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/rlds/oxe/materialize.py); [rlds/dataset.py L517-521](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/rlds/dataset.py)). Open issues #312 and #227 show users stuck on exactly this custom-RLDS friction with no maintainer answer ([openvla#312](https://github.com/openvla/openvla/issues/312); [openvla#227](https://github.com/openvla/openvla/issues/227)).

**Rank 1: plain Dataset for both arms.** One Dataset class, one copied `finetune.py`, one frozen stats dict, no TensorFlow at train time. The correctness risk sits in ~40 lines that mirror `RLDSBatchTransform.__call__`, and it is cheap to retire: TensorFlow is a hard dependency of the openvla install regardless, so on day 5 pull one sample from `modified_libero_rlds` through the real `RLDSBatchTransform` and assert your `input_ids` and `labels` match token for token ([datasets.py L27-67](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/datasets.py#L27-L67)). The personalization arm needs N ∈ {50, 200} trajectories from `libero_object_no_noops`, and the rehearsal transitions need `libero_spatial_no_noops`; both live in the 10.2 GB `openvla/modified_libero_rlds` as 16 tfrecord shards per suite with images already rotated 180° by the builder ([HF dataset tree](https://huggingface.co/api/datasets/openvla/modified_libero_rlds/tree/main); [moojink LIBERO builder](https://github.com/moojink/rlds_dataset_builder/blob/main/LIBERO_10/LIBERO_10_dataset_builder.py)). A one-off ~30-line export that reads N episodes with `tensorflow_datasets` and writes `(image, instruction, raw 7-D action)` rows to Parquet feeds the same Dataset class; this is an inference from the pinned dependencies, not a documented workflow, but it is the simplest way to subset by trajectory count, which the RLDS loader does not expose. The one thing to remember is that the RLDS gripper is already flipped to +1 = open by `libero_dataset_transform`, while raw LIBERO/robosuite data uses -1 = open, so your export must apply the same clip-and-invert before the Dataset sees it ([transforms.py L827-841](https://github.com/openvla/openvla/blob/c8f03f4/prismatic/vla/datasets/rlds/oxe/transforms.py#L827-L841)).

**Rank 2: RLDS via stock `finetune.py`.** Worth it only if the plain path fails the token-parity test and you cannot see why. It costs the builder authoring, the two registry edits, the stats patch, and the `tfds build` cycle. The 170-line `LIBERO_*_dataset_builder.py` in moojink's fork is the template if you go here, since it already matches the HDF5 layout of `regenerate_libero_dataset.py` ([moojink/rlds_dataset_builder](https://github.com/moojink/rlds_dataset_builder)).

**Rank 3: LeRobot → RLDS converter. Not worth adopting.** any4lerobot's `lerobot2rlds` is active (1.2k stars, pushed 2026-09-06) but derives RLDS keys from LeRobot column names, which do not match the `image`/`wrist_image`/`state` keys `libero_dataset_transform` expects, so you still write `configs.py`/`transforms.py` entries; nobody has reported running its output through `finetune.py` ([lerobot2rlds README](https://github.com/Tavish9/any4lerobot/blob/main/lerobot2rlds/README.md)). It inherits every Rank 2 cost plus a naming reconciliation and gives back nothing the Parquet export does not.

This ranking also settles the benign-movement data question, and it overrides PLAN.md's day-0 accelerant. The plan assumed FSHOA L0 episodes could be filtered by task string from `LIBERO-Safety/libero_safety`. They cannot: the dataset has exactly 15 task strings, all L0 names, and the five obstacle-avoidance tasks (`task_index` 10-14) carry 1,908-1,968 episodes each versus 991-1,000 for the other ten, consistent with TSA and FSHOA pooled under identical strings with no level or suite field anywhere in `meta/` ([tasks.jsonl](https://huggingface.co/datasets/LIBERO-Safety/libero_safety/blob/main/meta/tasks.jsonl); [episodes.jsonl](https://huggingface.co/datasets/LIBERO-Safety/libero_safety/blob/main/meta/episodes.jsonl)). Worse, the actions are the literal next-frame EEF displacement in meters: `actions[t,:3] == state[t+1,:3] - state[t,:3]` exactly in the inspected parquet, with std ≈ 5-7 mm per step and `|max|` ≈ 0.1, versus the ±0.94 normalized OSC commands OpenVLA's LIBERO checkpoints emit; they were generated for the fork's `output_max=2` controller, and the rotation dims correlate only 0.70/0.99/−0.99 with state deltas, so their representation is unverified ([stats.json](https://huggingface.co/datasets/LIBERO-Safety/libero_safety/blob/main/meta/stats.json); [episode_000000.parquet](https://huggingface.co/datasets/LIBERO-Safety/libero_safety/blob/main/data/chunk-000/episode_000000.parquet)). Reading it also means either pinning `lerobot==0.3.3` (the last v2.1-native release; `main` raises `BackwardCompatibilityError`) or raw `pyarrow` plus AV1 decoding ([lerobot datasets/utils.py](https://github.com/huggingface/lerobot/blob/main/src/lerobot/datasets/utils.py)). Go straight to the plan's fallback: benign movement labels from P's own successful rollouts on the benign instruction, supplemented by the scripted OSC waypoint fixture toward the target object, both of which emit actions in exactly the convention P was trained on. Say so in the paper.

## One Docker image, one A100 80 GB, under $100 of compute

The only version set with multiple independent reproductions is the upstream pin: Python 3.10, torch 2.2.0 / torchvision 0.17.0, transformers 4.40.1, tokenizers 0.19.1, timm 0.9.10, peft 0.11.1, draccus 0.8.0, tensorflow 2.15.0, tensorflow_datasets 4.9.3, flash-attn 2.5.5, and the README says explicitly that later transformers/timm/tokenizers caused regressions ([pyproject.toml](https://github.com/openvla/openvla/blob/c8f03f4/pyproject.toml); [README Installation](https://github.com/openvla/openvla/blob/c8f03f4/README.md#installation)). The best public recipe is the `Sidharth-82/OpenVLA-Custom-Eval-Layer` Dockerfile, which reproduced LIBERO-Spatial at **83.6% (418/500, Wilson CI 80.1-86.6%) versus the published 84.7 ± 0.9%** from a cold build on an A10G on 2026-08-27 ([Dockerfile](https://raw.githubusercontent.com/Sidharth-82/OpenVLA-Custom-Eval-Layer/main/src/docker/Dockerfile); [README](https://github.com/Sidharth-82/OpenVLA-Custom-Eval-Layer)). Its choices, consolidated with LIBERO's issue tracker, give the recipe:

```
FROM nvidia/cuda:12.1.1-cudnn8-devel-ubuntu22.04
apt: python3.10 cmake ninja-build ffmpeg libegl1 libgl1 libglew-dev libosmesa6-dev \
     linux-headers-generic libmagickwand-dev imagemagick libfontconfig1-dev
ENV MUJOCO_GL=egl PYOPENGL_PLATFORM=egl NVIDIA_DRIVER_CAPABILITIES=all HF_HOME=/workspace/hf
pip install torch==2.2.0 torchvision==0.17.0 torchaudio==2.2.0 --index-url https://download.pytorch.org/whl/cu121
git clone openvla @ c8f03f4 && pip install -e .          # brings transformers 4.40.1, peft 0.11.1, tf 2.15.0, draccus 0.8.0
pip install packaging ninja && MAX_JOBS=4 pip install flash-attn==2.5.5 --no-build-isolation   # source build, tens of minutes
pip install -r experiments/robot/libero/libero_requirements.txt   # robosuite==1.4.1 bddl easydict cloudpickle gym imageio[ffmpeg]
pip install numpy==1.26.4 mujoco==2.3.7 transformers==4.40.1 tensorflow-metadata==1.14.0 wandb==0.17.9 scipy pyarrow
git clone LIBERO (master) /opt/LIBERO ; git clone LIBERO-Safety (main) /opt/LIBERO-Safety
pip install usd-core>=25.5 wand scikit-image                         # LIBERO-Safety extras only; never its requirements.txt
unzip assets.zip -> /opt/LIBERO-Safety/libero/libero/assets/        # 10.7 GB from HF LIBERO-Safety/libero_safety_assets

```

Four details in that block each save a day. flash-attn 2.5.5 has **no cu12 wheel for torch 2.2 / cp310** (the release ships only cu118 wheels for that combination), so it compiles from source and needs the `-devel` image, `ninja`, and `MAX_JOBS=4` on small pods; bake it once ([flash-attention v2.5.5 assets](https://api.github.com/repos/Dao-AILab/flash-attention/releases/tags/v2.5.5)). The eval loader hardcodes `attn_implementation="flash_attention_2"` with no flag, and a 2026 reporter attributed a 74% vs 84.7% gap to running without it, so keep flash-attn rather than editing to `sdpa`, which RLinf shows loads and runs but nobody has shown reproduces the numbers ([openvla_utils.py L31-72](https://github.com/openvla/openvla/blob/c8f03f4/experiments/robot/openvla_utils.py#L31-L72); [openvla#333](https://github.com/openvla/openvla/issues/333); [RLinf PR #1578](https://github.com/RLinf/RLinf/pull/1578)). `mujoco` must be 2.3.7, not 3.x: robosuite 1.4 binds against 2.3, and MuJoCo 3.6 makes the `on_the_ramekin` bowl drop and slide ~1.6 cm after `set_init_state`, which would silently break paired-state determinism ([LIBERO issue #141](https://github.com/Lifelong-Robot-Learning/LIBERO/issues/141)). Do not `pip install -e` LIBERO's own `requirements.txt` (transformers 4.21.1, torch 1.11) nor LIBERO-Safety's (transformers 4.21.1, robomimic 0.2.0); install both clones via `PYTHONPATH` and switch, because both register the top-level package `libero` and the fork's README says to uninstall upstream first ([LIBERO-Safety requirements.txt](https://raw.githubusercontent.com/LIBERO-SAFETY/LIBERO-Safety/main/requirements.txt); [LIBERO-Safety README](https://github.com/LIBERO-SAFETY/LIBERO-Safety/blob/main/README.md)). Use upstream LIBERO for `libero_spatial`/`libero_object` so Uold/Unew are comparable to published numbers, and the fork only for FSHOA. `egl-probe` needs CMake and `evdev` needs kernel headers, and a missing `~/.libero/config.yaml` triggers an interactive `input()` on first import that hangs headless jobs ([LIBERO issue #38](https://github.com/Lifelong-Robot-Learning/LIBERO/issues/38); [libero/__init__.py L65-71](https://github.com/Lifelong-Robot-Learning/LIBERO/blob/master/libero/libero/__init__.py)). If `MUJOCO_GL=egl` fails with "Cannot initialize a EGL device display," the container is missing graphics capabilities; set `NVIDIA_DRIVER_CAPABILITIES=all` and fall back to `MUJOCO_GL=osmesa` only as a last resort ([LIBERO issue #115](https://github.com/Lifelong-Robot-Learning/LIBERO/issues/115)).

On GPU choice, the A100 80 GB is the right card and RunPod is the right vendor. LoRA r=32 at batch 16 uses about **72 GB** on an A100 80 GB per the README, and the script header says 48 GB fits batch 12 and 80 GB batch 24; no measured number exists for a 48 GB card, so an L40S ($1.09/h) or A6000 ($0.53/h) at batch 8 × accumulation 2 is plausible but unverified and not worth the day of debugging if it OOMs ([README](https://github.com/openvla/openvla/blob/c8f03f4/README.md); [finetune.py L7-11](https://github.com/openvla/openvla/blob/c8f03f4/vla-scripts/finetune.py#L7-L11)). On-demand list prices fetched 2026-09-20: RunPod A100 80 GB **$1.59/h secure ($1.19-1.39 community)**, H100 SXM $3.49/h, L40S $1.09/h, A6000 $0.53/h; Lambda A100 40 GB $1.99/h, H100 PCIe $3.29/h, with the 80 GB A100 only in 8× nodes ([RunPod pricing](https://www.runpod.io/pricing); [Lambda GPU cloud](https://lambda.ai/service/gpu-cloud)). An H100 is not worth the premium because eval dominates the budget and vanilla OpenVLA inference is **4.2 Hz (0.24 s/action)** on an A100, latency-bound by seven sequential decode steps ([OFT paper Table II](https://arxiv.org/html/2502.19645v1)). Put `HF_HOME`, both LIBERO clones, the 10.2 GB RLDS set, the 10.7 GB assets zip and `runs/` on a RunPod network volume at $0.07/GB/month (~$14 for 200 GB) so a pod restart or GPU swap costs nothing ([RunPod network volumes](https://docs.runpod.io/storage/network-volumes)). Pre-download with `hf download openvla/openvla-7b-finetuned-libero-spatial --local-dir ...`, `hf download openvla/modified_libero_rlds --repo-type dataset --include "libero_spatial_no_noops/*" --include "libero_object_no_noops/*"`, and `hf download LIBERO-Safety/libero_safety_assets --repo-type dataset` ([HF CLI guide](https://huggingface.co/docs/huggingface_hub/en/guides/cli); [assets repo](https://huggingface.co/datasets/LIBERO-Safety/libero_safety_assets/tree/main)).

The cost sketch for the T2 shape in PLAN.md (6 alignment jobs of ~750 updates, 9 personalization jobs, ~1,500 closed-loop episodes at 50 per class, plus Uold/Unew at 10-20 trials per task) is dominated by rollouts. No primary source gives vanilla OpenVLA LoRA seconds per step; the paper's "10-15 hours on a single A100" for a task fine-tune brackets a batch-16 step at roughly 1.5-2.5 s, so a 750-update job is 20-30 minutes and fifteen of them are under 8 GPU-hours ([OpenVLA paper](https://arxiv.org/pdf/2406.09246)). An episode at ~0.28 s per step (0.24 s inference plus sim and render) runs 220 steps at most on `libero_spatial`, so 1,500 hazard episodes plus a few hundred suite episodes is on the order of 25-35 GPU-hours. At $1.59/h that is **$55-70 for compute, $70-90 all-in with storage**, comfortably inside the $200 cap; measure seconds per step in the first 100 updates and seconds per episode on day 3 before trusting it. The one throughput lever that costs nothing is running two or three independent eval processes on the same 80 GB card, since each holds ~15 GB of weights and `predict_action` is single-sample.

## Conclusion

The sprint's engineering risk is inverted from what the plan's day-by-day table implies. The code that must be written is small and mostly mechanical, and every piece of it has a stock OpenVLA or LIBERO function to mirror; the environment is where days disappear, and the two forks in the plan (LIBERO-Safety's vendored controller, LIBERO-Safety's LeRobot dataset) are both traps that the earlier substrate report's "drop-in" framing did not surface. Treating LIBERO-Safety as a source of BDDLs, hand assets, init states and one predicate patch, while running it on OpenVLA's own robosuite pin and generating movement labels from the checkpoint itself, keeps a single action convention across every arm and removes the only dependency (`lerobot`) that would have forced a second Python environment.

Two implications follow for the paper. Because the plain-Dataset route is the maintainers' documented but "less tested" path, the token-parity test against `RLDSBatchTransform` is not optional hygiene but the evidence that the training objective was OpenVLA's, and it belongs in the released tooling. And because the merged checkpoint's `config.json` inherits the base model's stats unless you overwrite it, the "merge → fresh adapter → reload" step that Gate B checks for drift is also the step most likely to hide a normalization-key error; checking that the reloaded model's `norm_stats` has exactly one key before any rollout is the cheapest assertion in the whole pipeline.
